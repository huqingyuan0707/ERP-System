# ERP 项目代码生成规则

适用范围：适用于本仓库全部前后端代码生成（含新增功能、改动、重构、自动生成代码）任务，每次代码生成时始终生效。

> 禁止生成过度防御的冗余代码，严格遵守

## 1. 防御与校验

- 不要为猜测、极低概率的竞态、边界安全场景增加复杂度。
- 如果你认为防护逻辑必须添加，先说明出错场景、发生概率、新增代码量，确认后再实现，禁止私自扩大改动范围。
- 外部传入数据仅在入口校验一次；内部流转、类型已经确定的值，不要重复防御检查。

## 2. 函数与流程

- 不要提前抽取只用一次的函数。仅在逻辑可复用、封装复杂逻辑、代表独立清晰概念时才抽函数。
- 主函数只保留正常主流程，校验、细节分支下沉到子函数。

## 3. 注释

- 注释只写不明显的约束、反直觉逻辑，显而易见的代码不加注释。

## 4. 生成物

- 自动生成的文件不要零散手改，修改源头后整体重新生成。

## 5. 测试

- 测试针对真实实现，不要把业务逻辑复制进测试代码，尽量少用 mock。

## 6. 依赖与流程

- 遵循仓库现有规范，不要引入仓库未使用的工具、依赖和流程。

## 7. 与既有规则的衔接与冲突处理

- 本文件与 `code-style.md` 并行生效：命名、分层、目录结构、接口响应、类型、业务一致性、Git 提交等规范仍以 `code-style.md` 为准，本文件只约束「生成什么样的代码」。
- 注释策略以 `code-style.md` 第 12 节为准：代码生成阶段（新增或修改有效代码行）仍须为每一行有效代码添加中文注释，逐行注释优先。
- 本文件第 3 节「注释只写不明显的约束、反直觉逻辑，显而易见的代码不加注释」仅适用于不涉及新增/修改有效代码的场景（如说明性文字、配置文件说明），不得用来减少有效代码的逐行注释。
- 文档注释要求不受影响：模块/类/函数 docstring、前端文件头块注释、类型字段含义等仍按 `code-style.md` 执行。
- 其余未提及的规则若出现不一致，以更贴近本文件生成原则的一方为准，并需在完成回报中说明，不得静默扩大改动范围。
