# 提交前深度功能审查（deep-functional）

> 定位：在 `git commit` 之前，对本次工作树做一次「静态检查 + 深度审查 + 功能验证」的闭环审查。
> 只自动修**明确且获准**的 P1；P2/P3 只登记为 open，不顺手改。
>
> 本规程只约束审查过程，不修改任何代码、CI 配置或既有规则文件。
> 与流程图一致：读取规则与 Git 状态 → 范围清单与证据表 → 扫描与深度审查 → 基线验证 → 独立证伪 → 修复循环（最多三轮）→ 真实路径验收 → 最终 diff 复核 → 交付。
>
> 硬约束：**不暂存（不 `git add`）、不提交、不推送**；缺环境或缺证据时如实记「未验证 / open」，禁止写成「通过」。

---

## 〇、快速执行清单

一次完整审查按下面顺序走，任何一步都不能因为「看起来没问题」而跳过：

1. 读规则、读 Git 三态（暂存 / 未暂存 / 未跟踪），列出本次范围。
2. 建「文件 × 必查维度」证据表，逐格填证据或写 N/A 理由。
3. 跑静态检查、安全初筛、独立 Bug 扫描，做深度审查。
4. 即使零缺陷也跑基线：类型检查、相关 pytest、前端 type-check / build。
5. 每条候选问题交给只读复核者证伪；证据不足的记 E3 / open。
6. 只修明确且获准的 P1；修前分层备份，先写回归用例并证明修改前失败。
7. 修复后刷新范围、作废旧证据、重跑相关检查，再由 B 做覆盖审计。
8. 最多三轮；重复问题或连续两次验证失败立即停止。
9. 走真实用户路径验收，再做最终 diff 深度复核。
10. 交付范围清单、逐项证据、缺陷台账、度量、未验证边界。

## 一、总则与适用范围

### 1.1 角色

| 角色 | 职责 | 写权限 |
|---|---|---|
| A：执行者 | 读代码、跑检查、写证据、在授权范围内修 P1 | 可改代码；不得暂存/提交/推送 |
| B：独立只读复核者 | 证伪候选问题、做覆盖审计、最终验收 | **只读**，不得编辑、暂存、提交、推送，不得改测试来「制造通过」 |
| 授权人 | 确认是否允许本轮自动修 P1、是否接受 open 项交付 | 决定权 |

B 必须是「另一个」审查者：不能复用 A 的结论，不能只看 diff 片段，必须沿调用链读实现、默认值、异常路径、迁移与测试。

### 1.2 必须走完整 deep-functional 的改动

命中任一条件即走完整流程：

- `backend/app/**`：接口、Service、Repository、Model、Schema、权限依赖、配置、安全。
- `backend/alembic/versions/**`：任何迁移，包括只加索引、只改默认值。
- `backend/tests/**`：仅当同时改了生产行为或测试断言口径时；纯新增无关测试可按精简路径。
- `frontend/src/**`：API 封装、类型、Store、路由、权限指令、页面逻辑。
- `scripts/**`、`.github/workflows/**`：门禁、部署、备份、AI 评审脚本。
- `docker-compose.yml`、`nginx/**`、`.env.example`、`frontend/.env.production` 等配置模板。
- 依赖版本变更（`requirements.txt`、`frontend/package.json`、`pnpm-lock.yaml`）：涉及供应链与运行环境。

高风险路径（财务 / 库存 / 成本 / 单据 / 权限 / 迁移）**不得豁免**，即使只改一行。

### 1.3 可走精简路径的改动

只做「阶段一 + 最小静态检查 + 基线中的相关项 + 交付记录」，不做完整证伪与修复循环：

- 纯 `docs/**`、根目录 `*.md` 文档，且不改命令、配置、接口说明。
- 纯注释、纯格式化（pyink / ruff `--fix` 产生，且人工确认无语义变化）。
- 纯静态资源文案、样式，无逻辑分支。
- 仅改测试代码且不改变被测生产行为（仍须跑对应测试）。

精简路径必须在交付里写明「为何豁免、跳过了哪些阶段」。

### 1.4 P1 / P2 / P3 定级标准

| 级别 | 判定标准 | 本仓库典型例子 | 默认动作 |
|---|---|---|---|
| **P1** | 会造成数据错误、运行期必然崩溃、越权、事务/幂等失效，或核心用户路径不可用 | 金额/数量/成本算错；`inv_stock` 与 `inv_stock_flow` 不同事务；访问不存在的 `tenant_id`；未定义名称 / 非法调用 / 参数不匹配；跨租户读写或下载；迁移丢数/改数；登录失败、白屏、动态路由 403、列表 500；`vue-tsc` / `build` 失败 | 明确且获准则修；否则 `P1-open` 并请求授权 |
| **P2** | 有明确缺陷，但影响受控、可恢复，或只在边界条件下出现 | 特定边界返回 500/422 但提示不清；导出/任务边界；非核心页面交互错误；性能明显退化；缺少针对新规则的测试；高风险模块的类型告警但未证实会导致错误 | 只登记 open，不自动修 |
| **P3** | 无行为影响，或仅影响可读性/一致性 | 格式、命名、行宽、注释、文档、复杂度、重复代码、构建 chunk 过大、依赖弃用警告 | 只登记 open，不自动修 |

补充判定：

- CI 已阻断的错误类（pylint `E`、pytype `attribute-error` / `wrong-arg-*` / `annotation-type-mismatch`、ruff `F`）一律先按 P1 候选处理，再按实际影响复核。
- 高风险模块的 `unsupported-operands` / `container-type-mismatch` 按现有门禁视为阻断，属于 P1 候选。
- 同一根因导致多处表现，按「一个缺陷 + N 处证据」登记，不重复计数。
- 仅命中高风险路径、但没有具体缺陷证据的，按候选问题送 B 证伪，不得直接定 P1。

### 1.5 「明确 P1」与「获准」的判定

同时满足才算「明确」：

1. 触发条件可描述（输入、数据状态、权限、并发、配置）。
2. 影响落点可指出（哪个接口、哪张表、哪个页面、哪条金额/库存）。
3. 有可复核证据（命令输出、测试失败、行号、调用链），不是「可能」「建议检查」。
4. 最小修复范围明确，不牵连无关重构。
5. 本轮任务已授权修改代码。

缺任一条：登记为 `open` / `E3`，不编辑代码。

### 1.6 审查边界

- 不改 CI、pre-commit、规则文件；发现冲突只在本规程第十节记录。
- 不操作生产库、不读取开发 `.env` 真实值、不连接业务 PostgreSQL 做写操作。
- 迁移验证只在一次性测试库或 CI 的 `erp_test` 上做。
- 备份只写系统临时目录，不写进仓库；不产生待提交的临时产物。

### 2.2 读取 Git 三态

在仓库根目录执行：

```powershell
Set-Location "e:\erp系统"
git rev-parse --show-toplevel
git branch --show-current
git status --short
git diff --cached --name-status
git diff --name-status
git ls-files --others --exclude-standard
```

口径：

| 类别 | 命令 | 含义 | 审查要求 |
|---|---|---|---|
| 暂存 | `git diff --cached` | 已 `git add`、将进入下次提交 | 必须逐文件审；证据标注 `staged` |
| 未暂存 | `git diff` | 工作树中未 add 的修改 | 必须逐文件审；证据标注 `unstaged` |
| 未跟踪 | `git ls-files --others --exclude-standard` | 新文件，Git 尚未管理 | 先确认是否属于本次任务；属于才纳入，证据标注 `untracked` |

`git status --short` 常见组合：

- `M `：只有暂存区有修改。
- ` M`：只有工作树有修改。
- `MM`：同一文件暂存区与工作树都有修改，**两版都要审**。
- `A `：新增且已暂存。
- `??`：未跟踪。
- `R `：重命名（配合 `git diff --cached --stat` 看相似度）。

同一文件出现 `MM` 时，用 `git diff HEAD -- <file>` 看「相对上次提交的合并结果」，再分别看 `--cached` 与工作树版本，避免只审一半。

未跟踪文件不要 `git add` 后再看 diff（违反「不暂存」）。直接读文件内容并记录行号；需要 diff 形态时用：

```powershell
git diff --no-index -- /dev/null "frontend/src/新文件.ts"
```

说明：`git diff --no-index` 发现差异时退出码为 1，这是正常结果，不代表命令失败。

不属于本次任务的未跟踪文件（例如其他会话留下的目录、个人笔记、临时脚本）必须在范围清单中显式列为「排除，原因」，不得顺手审查、不得暂存。

### 2.3 范围清单模板

```markdown
## 范围清单（第 N 轮 / 时间）

| 序号 | 文件 | Git 状态 | 改动摘要 | 风险级别 | 必查维度 | 是否本轮范围 |
|---|---|---|---|---|---|---|
| S-01 | backend/app/services/inventory.py | staged | 出库成本计算调整 | 高（库存） | D2/D3/D5/D7 | 是 |
| S-02 | backend/tests/test_inventory_rules.py | unstaged | 新增回归用例 | 高 | D7 | 是 |
| S-03 | frontend/src/views/base/goods/index.vue | untracked | 新增页面 | 中 | D1/D6/D7 | 是 |
| X-01 | PGSql.md | untracked | 个人笔记 | — | — | 否（与本任务无关） |
```

规则：

- 每个在范围内的文件必须至少对应一个必查维度；不能只写「已看过」。
- 文件风险级别取该文件命中的最高风险域（财务/库存/成本/单据/权限/迁移/普通）。
- 范围变化（新增改动、修复产生新改动）后必须重写清单并递增轮次。

### 2.4 「文件 × 必查维度」证据表

证据表是本规程的核心产物。每个「文件 × 维度」格子必须有结论，不能留空。

字段定义：

| 字段 | 含义 | 示例 |
|---|---|---|
| 证据 ID | 唯一编号，轮次内不复用 | `E-R1-012` |
| 文件 | 仓库相对路径 | `backend/app/services/inventory.py` |
| Git 状态 | staged / unstaged / untracked | `staged` |
| 维度 | D1~D10 | `D5` |
| 结论 | 通过 / 失败 / N/A / 未验证 | `失败` |
| 证据 | 命令、关键输出、行号、测试名 | `pytest tests/test_inventory_rules.py::test_xxx` 失败 |
| 轮次 | 第几轮采集 | `R1` |
| 状态 | 有效 / 作废 | 修复后旧证据标 `作废：受 S-01 修复影响` |

必查维度：

| 编号 | 维度 | 查什么 | 典型证据 |
|---|---|---|---|
| D1 | 接口契约 | Router 路径/方法、请求响应字段 camelCase、分页结构、前端 `types` 与 `api` 同步 | 对比 `backend/app/schemas` 与 `frontend/src/types`；`vue-tsc` |
| D2 | 事务与并发 | Service 是否单事务、是否提前 `commit`、Repository 是否只 `flush`、行锁、幂等键 | 读调用链；`test_postgres_concurrency.py` |
| D3 | 权限与租户 | `require_perm` 权限码、`tenant_id` 来源、跨租户查询、`data_scope`、任务/文件 owner | 定向测试；`git grep tenant_id` |
| D4 | 软删与唯一约束 | `is_deleted` 过滤、部分唯一索引、恢复/重建冲突、删除引用保护 | 迁移文件 + 模型 + 冲突测试 |
| D5 | 金额/库存/成本一致性 | Decimal 精度、数量非负、可用量恒等、库存与流水同事务、出库成本结转、应收应付生成 | 库存规则测试 + 服务代码 |
| D6 | 前端类型与路由 | `vue-tsc`、动态菜单路由、`v-perm`、props 工厂函数、禁止 `void` 模板绑定 | 类型检查、路由代码、页面验证 |
| D7 | 测试覆盖 | 新规则是否有对应用例、边界与失败路径、是否误用 mock、postgres 用例是否标注 | `pytest -k` / 测试文件 |
| D8 | 迁移与兼容 | `alembic upgrade/dowgrade/check`、回填是否阻断、是否改历史数据、是否幂等 | CI `db-migration`；一次性测试库 |
| D9 | 安全与敏感数据 | 明文密码、`password_hash` 外泄、`token_version`、密钥硬编码、日志脱敏 | 安全测试 + diff 初筛 |
| D10 | 错误处理与可观测 | `AppException` 错误码、全局处理器、操作日志、是否吞异常 | 读 Service/Router + 日志表测试 |

按文件类型的最小必查集合：

| 文件类型 | 必查维度 | 可 N/A 的维度与理由要求 |
|---|---|---|
| `backend/app/api/v1/endpoints/**` | D1、D3、D7、D10 | D2 仅当只做参数转发；D5 仅当不触库存/财务 |
| `backend/app/services/**` | D2、D3、D5、D7、D9、D10 | D1 仅当不改变出参；D6 恒 N/A |
| `backend/app/repositories/**` | D2、D3、D4、D5 | D1/D6/D10 可 N/A，需说明 |
| `backend/app/models/**`、`backend/alembic/versions/**` | D4、D5、D8、D9 | D6 恒 N/A；D1 视是否改字段对外 |
| `backend/app/schemas/**` | D1、D9、D10 | D2/D4/D5 仅当纯 DTO |
| `frontend/src/api/**`、`types/**` | D1、D6、D7 | 其余按需 |
| `frontend/src/views/**`、`router/**`、`stores/**` | D1、D3、D6、D7 | D2/D4/D5 通常 N/A，需说明 |
| `scripts/**`、`.github/workflows/**` | D2、D9、D10 | 其余按需 |
| `docs/**`、根 `*.md` | 仅一致性核对（命令/路径/字段是否与代码一致） | 精简路径 |

N/A 必须写理由，例如 `D5 N/A：仅改商品名称校验，不写库存与金额`。只写 `N/A` 视为未完成。

### 2.5 阶段一完成条件

- 三态文件全部归类，排除项有理由。
- 范围内每个文件都有必查维度。
- 证据表骨架已建立，后续每跑一条命令就落一格。

## 三、阶段二：静态/安全/独立 Bug 扫描与深度审查

### 3.1 静态检查（本仓库真实命令）

后端（Windows 本地）：

```powershell
Set-Location "e:\erp系统\backend"
.\.venv\Scripts\python.exe -m ruff check app tests
.\.venv\Scripts\python.exe -m pylint --rcfile=pylintrc --disable=all --enable=E --score=n app
.\.venv\Scripts\python.exe -m pyink --config=pyink.toml --check --diff app
```

只查本次改动文件（快检，等价 pre-commit 口径）：

```powershell
Set-Location "e:\erp系统\backend"
.\.venv\Scripts\python.exe ..\scripts\ci\quality_scan.py `
  --repo-root .. `
  --local app/services/inventory.py app/api/v1/endpoints/inventory.py
```

说明：

- `--local` 模式只跑 pylint，只检查给出的 `backend` 相对路径；退出码 0 表示门禁通过。
- 全量等价 CI（pyink + pylint + pytype）在 Linux 上执行：

```bash
python scripts/ci/quality_scan.py --repo-root . --reports backend/reports --tools pyink pylint pytype
```

- `pytype` 不支持 Windows，本地用 Docker 补跑：

```bash
bash scripts/ci/run_pytype.sh backend/app
```

前端：

```powershell
Set-Location "e:\erp系统\frontend"
pnpm run type-check
pnpm run build
.\node_modules\.bin\eslint.cmd src --ext .ts,.vue --no-fix
```

Windows 实测注意：在本机 `pnpm exec eslint . --ext .ts,.vue --no-fix` 会报 `No files matching the pattern "."`，改用上面的 `node_modules\.bin\eslint.cmd`。不要用 `pnpm run lint` 做审查，因为它带 `--fix`，会改文件。

结果处理：

- `ruff F`、pylint `E`、pytype `attribute-error` / `wrong-arg-*` 先记 P1 候选。
- pyink / 行宽 / 命名 / 复杂度记 P3。
- 工具自身崩溃、版本不符、报告缺失按「检查未完成」记 `未验证`，不得记通过（fail-closed）。

### 3.2 安全扫描（本仓库真实能力与缺口）

**现状先说清：仓库没有 SonarQube、bandit、pip-audit、trivy、gitleaks 的配置或工作流。** `docs/代码质量门禁方案.md` 与 workflow 注释里提到的 SonarQube 属于规划/职责划分，不是已接入的扫描。因此安全维度只能用下面三类证据，并在交付里注明「无 SAST，安全维度为人工 + 回归测试」。

1）敏感信息 diff 初筛（启发式，不是门禁）：

```powershell
Set-Location "e:\erp系统"
git diff --cached -U0 | Select-String -CaseSensitive:$false `
  -Pattern 'password|passwd|secret|api[_-]?key|private key|BEGIN RSA|BEGIN OPENSSH'
git diff -U0 | Select-String -CaseSensitive:$false `
  -Pattern 'password|passwd|secret|api[_-]?key|private key|BEGIN RSA|BEGIN OPENSSH'
git status --short | Select-String -Pattern '\.env|\.acr\.env|\.pem|\.key'
```

命中只代表「需要人工确认」，不自动定级；确认是硬编码密钥才 P1。

2）安全回归测试（真实存在）：

```powershell
Set-Location "e:\erp系统\backend"
.\.venv\Scripts\python.exe -m pytest `
  tests/test_config_security.py `
  tests/test_rbac_tenant_security.py `
  tests/test_data_scope.py `
  tests/test_permissions.py -q
```

涉及用户、角色、部门、任务、导出时，再加：

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_user.py tests/test_goods_transfer.py -q
```

3）部署配置安全（仅改 `.env*`、`docker-compose.yml`、`nginx/**`、`scripts/*.sh` 时）：

```bash

# 只做静态配置校验、不依赖运行中容器时：
SKIP_RUNTIME_CHECKS=1 bash scripts/check-env.sh
```

Windows 本地用 Git Bash / WSL 执行；没有环境就记「未验证（缺 bash/服务器环境）」。

4）人工安全清单（逐项在证据表落格）：

- 认证：密码只存 bcrypt 哈希；改密/重置/状态变更是否递增 `token_version`；旧 Token 是否立即失效。
- 授权：新增接口是否有 `require_perm`；权限码是否与前端 `v-perm` 一致；`*` 是否被滥用。
- 租户：`tenant_id` 是否只来自已认证用户，是否接受请求头切换；Repository 查询是否带租户条件。
- 文件：导出/下载是否同时校验租户与 owner；路径是否可穿越；文件名是否编码安全。
- 输入：导入 Excel 的数值/编码/分类路径是否校验；非法值是否被归零或静默吞掉。
- 日志：是否记录密码、Token、完整身份证/手机号；失败是否误写成功日志。

任一项无法验证 → 记 `未验证`，并写缺失环境。

### 3.3 独立 Bug 扫描

分两层，互不替代：

1）确定性扫描（可复现，优先信）：

- `ruff`、`pylint E`、`pytype`、`pytest`、`alembic check`。
- 对改动点做定向搜索，例如：

```powershell
Set-Location "e:\erp系统"

git grep -n "commit()" -- backend/app/repositories backend/app/services
git grep -n "FOR UPDATE" -- backend/app/repositories
git grep -n "is_deleted" -- backend/app/repositories
git grep -n "@router" -- backend/app/api/v1/endpoints
```

2）独立 AI 扫描（线索层，不是结论层）：

- CI 中的 `scripts/ai_review.py` 是真实存在的评审脚本，但它依赖 `GH_TOKEN` 与模型密钥，产出是提交/PR 评论；只有 `REVIEW_ENFORCE` 开启、总体 `HIGH` 且存在可定位的 `critical` / `major` 时脚本才以非 0 退出，是否真正阻断合并还取决于 GitHub 分支保护与事件类型。
- 本地不要直接跑它去发评论。用**另一个只读 AI 会话**做扫描，提示词见 3.5；它输出的每条问题都必须回到代码/测试取证，不能直接采信。
- 路径风险规则（`backend/app/services/inventory.py`、`finance`、`alembic/versions`、`core/security.py` 等）只表示影响面，不等于缺陷。

### 3.4 深度审查（按维度看实现，不只看 diff）

必做动作：

1. **沿调用链读三跳**：Router → Service → Repository/Model；涉及异步任务/导出时再读任务与文件下载链路。
2. **核对事务边界**：Service 是否一次业务一个事务；是否在 Repository 里 `commit`；库存与流水是否同一 `AsyncSession`；幂等包装是否 `commit=False`。
3. **核对租户与权限**：`TenantDep` 是否来自认证用户；每个查询是否带 `tenant_id`；权限码是否与 `require_perm`、前端 `v-perm`、迁移种子一致。
4. **核对软删与唯一约束**：唯一索引是否 `WHERE is_deleted = false`；删除后编码是否可复用；引用保护是否覆盖。
5. **核对金额/库存**：Decimal 是否量化；出库成本是否按变更前平均成本；锁定/释放是否误写流水；数量非负与可用量恒等约束。
6. **核对前端契约**：后端字段 camelCase 是否与 `frontend/src/types` 一致；动态菜单 `component` 路径是否存在；页面是否直接绑定只读 prop；模板是否出现 `void` 表达式。
7. **核对迁移**：`upgrade` 是否幂等；是否有 DDL 前 preflight；是否自动删/改历史数据；`downgrade` 是否可回。
8. **按需核对规格**：用 `需求条目拆分.md`、`API接口清单.md`、`数据库表设计.md`、`Vue3页面清单.md` 对照；文档与代码冲突时以代码现状为准，并在交付里单列。

深度审查必须回答三个问题：

- 正常路径对不对？
- 失败/回滚/并发路径对不对？
- 换了租户、权限、软删状态、空数据后还对不对？

## 五、阶段四：独立证伪（B 只读复核）

### 5.1 给 B 的输入

每条候选问题一张卡片：

```markdown
### 候选问题 C-001

- 来源：A 深度审查 / ruff / pylint / pytype / pytest / AI 扫描
- 文件与行号：backend/app/services/inventory.py:164
- 改动状态：staged / unstaged / untracked
- 触发条件：<输入、租户、权限、并发、配置、数据状态>
- 期望行为：<按需求/规范/接口契约>
- 实际行为：<读到的代码或命令输出>
- 已知证据：<命令、输出、测试名>
- A 的建议级别：P1 / P2 / P3
- 复现方式：<命令或步骤；没有就写「无」>
```

B 只拿到卡片与仓库，不拿 A 的结论性描述；B 必须自己读实现。

### 5.2 B 的核对动作

1. 确认触发条件是否真实可达：入口参数、权限依赖、默认值、配置分支。
2. 找保护逻辑：前置校验、数据库约束、异常处理、事务回滚、前端拦截。
3. 沿调用链核对实际影响：是否真的写错数据、越权、崩溃，还是只影响日志/提示。
4. 查已有测试与迁移：是否已被既有约束覆盖；测试是否只是没断言到。
5. 给出裁决，并说明证据。

禁止：

- 只看 diff 就下结论。
- 用「路径高风险」代替缺陷证据。
- 为了让问题成立而修改测试、放宽断言。
- 对无法运行的环境直接写「通过」。

### 5.3 裁决类型

| 裁决 | 含义 | 处理 |
|---|---|---|
| **推翻（false-positive）** | 保护逻辑/调用链已覆盖，候选不成立 | 记 `false-positive`，写明哪段代码/约束推翻了它；写入度量「推翻数」 |
| **成立（E1）** | 确定性代码路径即可证明，单进程可复现 | 进入同类搜索与重新定级 |
| **成立（E2）** | 可用现有测试/命令复现 | 保留复现命令作为证据；进入修复队列 |
| **证据不足（E3）** | 依赖真实 PG 并发、Redis、生产配置、浏览器交互等本地不具备的条件 | 单列 `E3-条件风险`，状态 `open/未验证`；不得当 false-positive，也不得当已修复 |
| **条件风险（E3）** | 只有特定配置/数据状态才触发，当前无法证明是否会发生 | 写明触发条件、缺失环境、复现方法；按最坏影响定级但不自动修 |

### 5.4 成立后搜同类问题并重新定级

按「同根因模式」搜索，而不是只修一处：

```powershell
Set-Location "e:\erp系统"

# 示例：租户条件缺失
git grep -n "select(" -- backend/app/repositories
git grep -n "tenant_id" -- backend/app/repositories backend/app/services

# 示例：Repository 提前提交
git grep -n "commit()" -- backend/app/repositories

# 示例：软删过滤缺失
git grep -n "is_deleted" -- backend/app/repositories

# 示例：权限码写法不一致
git grep -n "require_perm" -- backend/app/api/v1/endpoints

# 示例：前端模板 void 绑定
git grep -n "void " -- frontend/src
```

每个命中项都要单独取证：

- 读上下文，确认是否同一根因、是否真的可达。
- 能复现的给 E1/E2；不能的给 E3 + open。
- 按**实际影响**重新定级：核心财务/库存数据错误是 P1；只影响非核心页面提示是 P2；纯风格是 P3。不得因为「同类」就一律升 P1。

## 六、阶段五：修复循环（最多三轮，功能阶段修复也计入）

### 6.1 进入条件

同时满足才进入：

- 候选已被 B 判为「成立 E1/E2」；
- 级别为 P1，且实际影响符合 1.4；
- 本轮任务已获准修改代码；
- 未触发 6.6 的停止条件；
- 未超过三轮（阶段二/三/六中顺手改的代码也算一轮，不得绕过备份与回归）。

### 6.2 每轮七步

#### 第 1 步：首次编辑前分层备份

备份写到系统临时目录，不写仓库：

```powershell
Set-Location "e:\erp系统"
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$bak = Join-Path $env:TEMP "erp-deep-review\$stamp"
New-Item -ItemType Directory -Force -Path $bak | Out-Null

# L1：补丁层（暂存 + 未暂存）
git diff --cached > (Join-Path $bak 'staged.patch')
git diff > (Join-Path $bak 'unstaged.patch')

# L2：文件层（所有已跟踪改动 + 本次范围内未跟踪文件）
git diff --name-only HEAD | ForEach-Object {
  $dest = Join-Path $bak $_
  New-Item -ItemType Directory -Force -Path (Split-Path $dest) | Out-Null
  Copy-Item $_ $dest
}
git ls-files --others --exclude-standard | ForEach-Object {
  $dest = Join-Path $bak $_
  New-Item -ItemType Directory -Force -Path (Split-Path $dest) | Out-Null
  Copy-Item $_ $dest
}

Write-Output "备份目录：$bak"
```

涉及迁移/库存数据时再加 L3：

- 只对**一次性测试库**做 `pg_dump`，禁止对业务库执行。
- 记录库名、迁移版本、导出文件路径；没有测试库就记「未验证」。

恢复规则：

- 单文件恢复到备份：`Copy-Item (Join-Path $bak '相对路径') '相对路径'`。
- 未暂存改动被误改：优先用备份文件覆盖，不用 `git checkout --` 一把梭。
- 禁止 `git reset --hard`、`git clean -fd`、`git stash`（会打乱用户工作树）。

#### 第 2 步：先写回归验证，证明修改前失败

后端 P1 的最小回归用例（放在 `backend/tests/`，遵循现有 pytest 风格）：

```python
"""P1 回归：<一句话描述问题与业务影响>。"""

from __future__ import annotations

import pytest


@pytest.mark.asyncio
async def test_<场景>_<期望行为>(client):
    """修改前应失败：<具体断言>。"""
    # 1) 构造能触发缺陷的租户/权限/库存/金额数据
    # 2) 调用真实接口或 Service，不使用 mock 复制业务逻辑
    # 3) 断言业务结果，而不是断言实现细节
    ...
```

执行并**先确认失败**：

```powershell
Set-Location "e:\erp系统\backend"
.\.venv\Scripts\python.exe -m pytest tests/test_<模块>_regression.py::test_<场景>_<期望行为> -q
```

证据必须包含：失败断言/异常、实际值、期望值、时间。

前端 P1（无单测框架时）：

- 类型级问题：先让 `pnpm run type-check` 失败，保存报错。
- UI 级问题：写固定复现步骤（页面、账号、权限、点击顺序），保存 Console / Network 的实际响应，作为「修改前失败」证据。
- 不临时引入 Vitest/Playwright（仓库未使用，违反依赖规范）；没有工具就记 `未验证（缺前端 E2E）`。

迁移 P1：

- 在一次性测试库先执行 `alembic upgrade head`（或从故障版本升级），保存失败输出。
- 不在业务库上验证。

#### 第 3 步：做最小修复

约束：

- 只改触发缺陷的那条链路；不重构、不顺手格式化、不扩大范围。

### 6.6 停止条件（命中即停）

- **重复问题**：同一根因/同一复现命令在修复后再次出现，或同一缺陷第二次回到台账。停止，不再叠加补丁，交付说明根因未清除。
- **连续两次验证失败**：同一轮内回归验证连续两次未通过（不是环境抖动导致的重跑），停止，保留现场与失败输出。
- **达到三轮上限**。
- **没有明确 P1**：只剩 P2/P3 或 E3，停止修改。
- **未获授权**：需要改代码但本轮未被授权，停止并请求确认。
- **修复会扩大范围**：需要改公共接口/迁移/依赖/CI 才能修，停止并升级决策。

### 6.7 P1 / P2 / P3 的处理边界

- P1：按 6.1 条件修；修完必须走完七步。
- P2：只进缺陷台账，状态 `open`；不自动修，不因「顺手」改。
- P3：只记录；格式类可用 pyink/ruff 自动修复，但若改动文件，同样计入一轮并需要重跑基线。

### 7.5 最终 diff 深度复核

在最新工作树上执行：

```powershell
Set-Location "e:\erp系统"
git status --short
git diff --stat
git diff --cached --stat
git diff --cached
git diff
git diff --check
git ls-files --others --exclude-standard
```

复核内容：

1. 逐文件确认最终 diff 只包含本轮审查范围内的改动，没有混入无关文件。
2. 确认没有暂存动作、没有提交、没有推送。
3. 确认没有调试残留（`print`、`pdb`、`breakpoint`、临时 TODO）。
4. 确认没有密钥/真实 `.env` 值/临时产物进入 diff。
5. 原问题复现命令从失败变通过，且失败/通过输出都在证据里。
6. 同类搜索命中项逐条有裁决；新增 P1/P2 已登记。
7. 静态、基线、功能检查都在最终 diff 上重跑过。
8. B 做最终覆盖审计：无漏项、无失效证据、无未解释的 P1。

### 7.6 `fixed` 判定条件

同时满足才可标 `fixed`：

- 原问题有「修改前失败」证据，修复后有「修改后通过」证据。
- 同类问题已搜索并逐条取证。
- 最终 diff 上相关静态检查、基线、功能路径通过。
- B 独立验收确认原问题消失，且没有新增 P1/P2。
- 没有用放宽测试、跳过用例、mock 业务逻辑的方式「通过」。

否则状态只能是 `open` / `未验证` / `false-positive`，不能写 `fixed`。

| 复杂度、重复代码 | 规划中的 SonarQube（**当前未接入**） | 不声称已扫描；记「未验证」或人工抽查 |
| 业务语义、需求符合度、分层 | AI 评审（评论）+ 人工深度审查 | 独立证伪必须自己读调用链，不转述 AI 评论 |
| 单元/接口回归 | CI pytest | 本地至少跑相关测试；交付前跑非 PG 全量 |
| PG 并发、迁移往返 | CI postgres / db-migration | 有环境就跑；没有记未验证，不重复造测试 |
| 前端类型/构建 | CI frontend | 本地必跑 type-check + build |
| 真实用户路径 | **无 CI 覆盖** | 本规程阶段六新增，必须人工执行或记未验证 |

原则：

- pre-commit 是秒级反馈，不复制 CI；deep-functional 也不复制全量 CI，只在最终 diff 上跑相关基线。
- 静态工具能确定性发现的问题，不再让 AI 评审重复报告；AI 评审只提示业务语义与影响面。
- AI 评审的评论是线索，不是裁决；最终以代码、测试、数据库约束证据为准。

### 9.3 新增 / 替换了哪些环节

- **未新增或替换任何 CI 环节**。本规程是提交前的人工/本地闭环，可作为 PR 前的自检。
- 与现有环节的关系：
  - 替换：无。
  - 增强：在 CI 已有静态/测试之外，补上「独立证伪、同类搜索、修复回归、真实路径、最终 diff 复核」。
  - 前置：建议在开 PR 前完成阶段一至五，把 P1 与证据带入 PR；阶段六可在本地或预发环境完成。
- 若未来要接入 CI，建议插在 code-quality 之后、AI 评审之前（与现有文档顺序一致），但**本次不改配置**。

## 十、与流程图 / 仓库现状的差异说明

本节只记录差异与建议，不修改现有配置。

### 10.1 流水线平台差异

- 流程图与项目文档提到 GitLab CI / stage 顺序（pre-commit → 代码质量 → AI 评审 → SonarQube → SQL 校验 → 单元测试 → 预发部署）。
- 本仓库实际使用 **GitHub Actions**，没有 `.gitlab-ci.yml`。`ci.yml`、`code-quality.yml`、`ai-review.yml`、`db-migration.yml`、`deploy.yml` 是**独立 workflow**，彼此没有 `needs` 依赖，实际会并行触发；文档中的串行顺序并未被配置强制。
- 建议：不要把「AI 评审在单测之后」当作既成事实；以各 workflow 的实际触发与阻断为准。若需要串行门禁，需另开任务改 workflow（本次不做）。

### 10.2 SonarQube 并未接入

- `docs/代码质量门禁方案.md`、`code-quality.yml` 注释、`pylintrc` 都把复杂度/重复代码/安全漏洞划给 SonarQube，但仓库中没有 SonarQube 配置、workflow 或 scanner。
- 因此：
  - 不能写「已通过 SonarQube / SAST」。
  - 安全维度只能记「人工清单 + 安全回归测试 + 敏感信息初筛」，并在未验证边界写明「无 SAST」。
- 建议：后续单独引入 SonarQube 或 bandit/pip-audit；在此之前，deep-functional 不重复造扫描器。

### 10.3 Electron / Worker / Native / 媒体不适用

- 仓库是 Vue 3 Web + FastAPI 后端 + PostgreSQL/Redis，没有 Electron、原生客户端、独立 Worker、音视频链路。
- 流程图中的 `Electron / UI / Worker / Native / 媒体` 在本仓库映射为：
  - UI → 浏览器页面（登录、系统管理、基础资料、库存）；
  - Worker → 不适用，导出为同步文件响应；任务表只做记录与下载权限；
  - Native / 媒体 → 不适用。
- 交付里必须写 `N/A + 原因`，不能假装验过。

### 10.4 采购 / 销售 / 财务端到端暂不可走

- `backend/app/api/v1/endpoints/` 只有 auth、system、dicts、configs、export、goods、log、task、warehouse、inventory、supplier、customer；没有采购、销售、财务路由。
- `backend/app/services/finance.py` 存在，但没有对外入口与前端页面。
- 因此流程图中的「采购/销售/库存/财务路径」当前只能验库存与基础资料；采购/销售/财务记「未接入，N/A」，不能写「已验收」。

### 10.5 前端没有单测 / E2E 框架

- `frontend/package.json` 没有 Vitest、Playwright、Cypress；只有 `type-check`、`lint`、`build`。
- 前端 P1 的「回归验证先失败」只能用类型检查失败或固定手工复现步骤 + Console/Network 证据。
- 不建议为了本流程临时引入新测试框架（违反「不引入仓库未使用的依赖」）；缺工具就记 `未验证`。

### 10.6 Windows 本地工具差异

| 项 | 现状 | 处理 |
|---|---|---|
| pytype | 不支持 Windows，仅 CI Linux 或 Docker | 本地用 `bash scripts/ci/run_pytype.sh`，否则记未验证 |
| `pnpm exec eslint .` | 本机报 `No files matching the pattern "."` | 用 `.\node_modules\.bin\eslint.cmd src --ext .ts,.vue --no-fix` |
| `scripts/check-env.sh` | bash 脚本，面向 Linux 服务器 | Git Bash / WSL 执行，或记未验证 |
| `alembic check` | 需要可用数据库 | 一次性库或 CI；不对业务库执行 |

### 10.7 文档与代码现状不一致

- `README.md` 的「当前已完成」只列系统管理与基础资料（商品/分类/单位），但代码中已有客户、供应商、仓库、库存接口与页面，以及 `finance` 服务层。
- `README.md` 写分页参数为 `page` / `page_size`，但 `backend/app/schemas/common.py` 的 `PageQuery` 对外声明为 camelCase（`pageSize`）；以实际 OpenAPI 与 Schema 为准。
- `docs/AI评审整改说明.md`、`docs/B01-B05修复与验收记录.md` 记录了这些新增能力，`README.md` 未同步。
- 本规程以**代码现状 + API接口清单 + 需求条目拆分**为准；审查时若发现文档与代码冲突，在交付里单列，不擅自改文档。

### 10.8 pre-commit 只覆盖后端

- `.pre-commit-config.yaml` 只有通用卫生、pyink、pylint，没有前端 ESLint/Prettier 钩子。
- 前端改动必须靠 deep-functional 阶段二的 ESLint + type-check 兜底；不能因为 pre-commit 通过就认为前端没问题。

### 10.9 当前工作树快照（2026-11-02）

本次核对时的工作树并非干净状态：存在未暂存的 `数据库表设计.md` 修改，以及未跟踪的 `.trae/rules/code-generation.md`、`.zcode/`、`PGSql.md`。这些文件是否属于本次提交范围必须由执行者显式判断；不属于的任务外文件不得纳入审查或暂存。
