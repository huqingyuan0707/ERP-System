# 代码质量门禁落地方案（谷歌体系：pyink / pytype / pylint）

> 本文记录本项目引入 Google Python Style Guide 对齐的三件套（pyink、pytype、pylint）
> 的完整落地方案：工具分工、门禁分级、存量治理、与既有工具的职责边界。
> 文中所有结论均在本仓库真实代码上实测验证过，踩过的坑也一并记录。

---

## 一、工具分工

| 工具 | 定位 | 解决什么问题 | 阻断策略 |
|------|------|--------------|----------|
| **pyink** | 格式化 | 代码风格统一（Google Style） | **不阻断**，仅提示（可自动修复） |
| **pylint** | 语义检查 | 空引用、非法调用、参数不匹配、未定义变量 | 高风险模块**强制阻断** |
| **pytype** | 类型推断 | pytype 独有的数据流类型分析 | 高风险模块**强制阻断** |

### 为什么这样分工

ERP 系统的核心风险不是「代码好不好看」，而是**财务/库存数据算错**。
因此策略明确为：

> **优先阻断「类型错误、空引用、非法调用」；格式类问题只提示，不盲目阻断。**

格式问题可以一键自动修复，阻断它只会打断开发节奏，却拦不住任何真实的数据风险。

## 二、配置文件

### 2.1 `backend/pyink.toml`

**⚠️ 关键坑：pyink 只会读取文件内 `[tool.pyink]` 段中的键。**
若写成顶层裸键（`line-length = 88`），会被**静默忽略**——不报错，但也不生效。
实测确认：顶层裸键 + `--config` 指定文件 → 配置无效；`[tool.pyink]` 段 → 生效。

```toml
[tool.pyink]
line-length = 100                    # 与既有 ruff/black 对齐，避免互相打架
pyink-indentation = 4               # Google Python Style 用 4 空格（2 空格是给 JS 的）
target-version = ["py311"]
pyink-use-majority-quotes = true    # 用文件内多数派引号，不强制双引号
```

**为什么 line-length 用 100 而不是 Google 规范的 80？**
本仓 `pyproject.toml` 中 ruff/black 已是 100。若 pyink 用 80，两个格式化器会互相打架，
每次提交产生大量无意义 diff。**保持一致优先于形式上贴合规范。**

**为什么用「多数派引号」而不是强制双引号？**
存量代码单双引号混用，强制双引号会产生大面积无意义 diff，淹没真实业务改动。

### 2.2 `backend/pytype.cfg`

**⚠️ 关键坑 1：pytype 不会自动发现 `pytype.cfg`。**
默认只向上查找 `pyproject.toml` / `setup.cfg`，必须显式 `--config=backend/pytype.cfg`。

**⚠️ 关键坑 2：`python_version` 必须与运行解释器版本匹配。**
配置写 `python_version = 3.11` 时，用 Python 3.12 容器运行会报：
`Could not find a valid python3.11 interpreter in path (found Python 3.12.16)`。
**CI 必须用 Python 3.11。**

**⚠️ 关键坑 3：pytype 不支持 Windows，且仅支持 Python 3.8~3.12。**
官方明确「Windows is currently not supported unless you use WSL」。
因此 pytype **只在 CI（Linux + Python 3.11）运行**，本地 Windows 需用 Docker/WSL 补跑。

屏蔽的错误类型（每一条都有明确理由）：

| 屏蔽项 | 理由 |
|--------|------|
| `import-error` | pytype 解析 FastAPI/SQLAlchemy 2.0 运行时元数据时误报；项目自身的 import 错误由 pylint E0401 与单元测试覆盖 |
| `pyi-error` | typeshed 存根版本问题 |
| `module-attr` | 与 import-error 同源 |
| `bad-return-type` | FastAPI 依赖注入下返回值被推断为 Any，装饰器包装后推断不可靠 |

**刻意不屏蔽**：`attribute-error`（空引用）、`wrong-arg-types`（非法调用）——
这两类正是要阻断的核心，且实测能命中真实缺陷。

### 2.3 `backend/pylintrc`

**⚠️ 关键坑 1：`allow-global-unused-variables` 必须保持 `yes`（默认值）。**

改成 `no` 会导致 pylint 把「模块级定义、仅被装饰器注册」的 FastAPI 路由函数
判成 unused-variable——**实测一次性报出 227 条 W0612 假告警**，
74 个端点文件全部被淹没。原因是 FastAPI 的 `@router.get("/xxx")` 把函数注册到路由表，
装饰器返回的对象并非「函数本身」，pylint 变量检查器看不到该函数名在模块内被消费。

**⚠️ 关键坑 2：不要配置 `ignored-modules` 包含 sqlalchemy/fastapi。**
实测一旦配置，pylint 会连带失去对「模型属性不存在」的推断能力，
**E1101(no-member) 整体失效**——而 E1101 恰好能命中
`SysPermission.tenant_id` 这类「模型没继承 TenantMixin 却按 tenant_id 过滤」的真实缺陷
（运行期直接抛 AttributeError）。
保留 E1101 的代价是少量 SQLAlchemy 动态属性误报，这些由**存量基线**吸收，
不应通过关掉检查来规避。

**⚠️ 关键坑 3：`disable=all` 会导致 pylint 退出码 32（用法错误），不是 0。**
配置里不要出现 `disable=all`。

## 三、门禁分级策略

### 3.1 模块风险分级

由 `scripts/ci/quality_gate.py` 的 `HIGH_RISK_PATTERNS` 定义。
路径中命中任一关键字即为**高风险模块**：

| 领域 | 匹配关键字 |
|------|-----------|
| 财务 | finance、fin_、billing、payment、settlement、invoice、voucher、ledger、receivable、payable、profit |
| 库存 | inventory、stock、warehouse、transfer |
| 成本 | cost、pricing、valuation |
| 单据 | purchase、order、sales、return |
| 权限/幂等 | permission、role、idempotency、data_scope |
| 公共基础 | core/exceptions、core/security、utils/bill_no |

### 3.2 阻断规则

| 问题类别 | 高风险模块 | 普通模块 | 对应检查 |
|----------|-----------|---------|----------|
| 未定义变量 / 使用前未赋值 | **阻断** | **阻断** | pylint E0602/E0601 |
| 属性不存在（空引用） | **阻断** | **阻断** | pylint E1101、pytype attribute-error |
| 不可调用 | **阻断** | **阻断** | pylint E1102、pytype not-callable |
| 实参过多 | **阻断** | **阻断** | pylint E1121、pytype wrong-arg-count |
| 关键字参数不匹配 | **阻断** | **阻断** | pylint E1123/E1120、pytype wrong-keyword-args |
| 不可迭代 / 不可下标 | **阻断** | **阻断** | pylint E1133/E1136、pytype not-indexable |
| 类型不匹配 | **阻断** | **阻断** | pytype annotation-type-mismatch |
| 不支持的运算符 | **阻断** | 告警 | pytype unsupported-operands |
| 容器类型不匹配 | **阻断** | 告警 | pytype container-type-mismatch |
| 宽泛异常捕获 | 告警 | 告警 | pylint W0718 |
| 命名不规范 / 缺文档 / 行太长 | 告警 | 告警 | pylint C0103/C0116、ruff E501 |
| 复杂度 / 重复代码 | 告警 | 告警 | SonarQube 负责，此处不重复 |

**必须阻断的共性**：这些是「几乎必然是 bug」的问题——空引用、非法调用、参数不匹配。
**仅告警的共性**：这些是「可能有争议」的问题——风格、命名、复杂度偏好。

### 3.3 为什么不用 pylint 的 `--fail-on`

实测发现 `--fail-on` 语义**不一致**：

| 写法 | 行为 |
|------|------|
| `--fail-on=E0602` | 会**复活**被 `disable` 的检查（退出码含错误位） |
| `--fail-on=E`（类别） | **不会**复活被 disable 的检查 |

两种写法行为相反，极易误阻断。因此门禁**不用 `--fail-on`**，
改为解析 JSON 输出后自行分级判定（`scripts/ci/quality_gate.py`）。

## 四、存量代码治理

### 4.1 基线机制

存量 44 个问题若全部阻断，会让所有 MR 都无法合并。
解法是**基线（baseline）**：

- `backend/quality_baseline.json` 记录当前已存在的问题指纹
- 基线内的问题**不阻断**，只在报告中提示
- 基线外的新问题按分级策略判定

**指纹设计**：`文件路径 | 消息ID | 归一化消息`
其中消息会把引号内容和数字替换掉（`'abc'` → `'X'`，`123` → `N`），
这样**行号漂移、变量名变化不会导致同一问题被误判为「新问题」**。

**阻断类问题不收录进基线**——它们即使已存在也应当被修掉，不应被长期豁免。

更新基线：
```bash
cd backend
python ../scripts/ci/quality_gate.py \
  --pylint-json reports/pylint.json \
  --baseline quality_baseline.json --update-baseline \
  --output reports/quality --repo-root .. --work-dir .
```

### 4.2 批量修复

```bash
# 自动修复格式化（安全）
cd backend && pyink --config=pyink.toml app

# 自动修复 ruff 可修项
ruff check app --fix

# pylint 可自动修复项
pylint --rcfile=pylintrc --fix app
```

### 4.3 屏蔽规则写法

**pylint**（行内，必须写明原因）：
```python
# pylint: disable=too-many-arguments  # 报表导出需接收完整筛选条件集合
```

**pytype**（行内或块级）：
```python
# pytype: disable=unsupported-operands  # Redis 降级分支导致，见上方注释
```

**pytype 屏蔽位置限制**：`disable` 指令只对**所在行之后**生效。
若报错在函数签名行，屏蔽指令必须放在函数定义**之前**，否则会报
`late-directive`（指令位置过晚）。

## 五、与既有工具的职责划分

流水线顺序：
```
pre-commit（本地）→ 代码质量门禁 → AI 代码评审 → SonarQube → SQL 校验 → 单元测试 → 预发部署
```

**代码质量门禁放在 AI 评审之前**的理由：
静态检查是确定性的、秒级的。先把「机器能确定发现的问题」挡在前面，
既避免带低级错误的代码消耗 AI 评审的 token，也避免 AI 评审去重复报告
pylint 已经能报的东西。

| 工具 | 负责 | 不负责 |
|------|------|--------|
| ruff | import 排序、基础风格、快速 lint | 类型分析、语义缺陷 |
| pyink | 格式化 | 逻辑正确性 |
| pylint | 语义正确性（空引用、非法调用） | 类型推断、复杂度、重复代码 |
| pytype | 类型推断与数据流分析 | 风格、复杂度 |
| SonarQube | 复杂度、重复代码、安全漏洞、覆盖率 | — |
| AI 代码评审 | 业务语义、需求符合度、架构分层、代码异味 | 机械可查的语法/类型问题 |

**SQL 校验**（`db-migration.yml` 的 `alembic check`）与本门禁不重叠：
前者校验「模型与迁移文件是否一致」，后者校验「代码本身是否正确」。

## 六、报告格式（供效能看板接入）

产出两个文件，位于 `backend/reports/quality/`：

### `quality-report.json`

```json
{
  "schemaVersion": "1.0",
  "meta": {
    "branch": "feature/xxx",
    "commit": "abc123",
    "mergeRequest": "42",
    "pipeline": "12345",
    "timestamp": "2026-11-01T13:00:00Z",
    "scope": "backend/app"
  },
  "summary": {
    "total": 44,
    "new": 3,
    "baseline": 41,
    "blocking": 1,
    "highRiskBlocking": 1,
    "byCategory": { "no-member": 2, "unused-variable": 1 },
    "byTool": { "pylint": 44, "pytype": 0 }
  },
  "findings": [
    {
      "tool": "pylint",
      "file": "backend/app/services/inventory.py",
      "line": 164,
      "column": 12,
      "messageId": "E1101",
      "category": "no-member",
      "message": "Class 'InvStock' has no 'tenant_id' member",
      "severity": "error",
      "isHighRisk": true,
      "isNew": true,
      "blocking": true
    }
  ]
}
```

### `quality-report.md`

人读版，直接作为 PR 评论发布（workflow 已自动实现，含旧评论替换逻辑，避免刷屏）。

### 接入效能看板

- **CI 产物**：workflow 通过 `actions/upload-artifact` 上传，保留 30 天
- **实时采集**：可直接消费 `quality-report.json`，建议关注的指标：
  - `summary.blocking` — 阻断问题数（合并质量门禁 KPI）
  - `summary.new` — 新增问题数（代码健康度趋势）
  - `summary.byCategory` — 问题类型分布（定位系统性缺陷）
  - `findings[].isHighRisk` — 高风险模块问题占比（数据正确性风险）
- **PR 评论**：评审者无需翻流水线日志即可看到阻断项清单

## 八、落地过程中实际修复的缺陷

引入这套工具后，**静态检查实际命中了 6 个真实缺陷**（均为运行期会崩溃或行为错误的问题），
这正是本方案的价值所在：

| 缺陷 | 位置 | 后果 |
|------|------|------|
| 缺 `sqlalchemy.select` 导入 | `app/services/finance.py` | 对账查询运行期 NameError |
| 多传 `created_by` 参数 | `app/api/v1/endpoints/goods.py` | Redis 未配置时 TypeError |
| 访问不存在的 `SysPermission.tenant_id` | `app/repositories/permission.py` | 查询运行期 AttributeError |
| `_idem_check` 返回类型标注错误 | `app/api/v1/endpoints/inventory.py` | 元组解包被标成 Service，静态不可检 |
| `dept_id_column` 标注为 `object` | `app/core/data_scope.py` | 掩盖了 `.in_()` 调用，静态不可检 |
| `Workbook.active` 未做空值守卫 | `app/utils/excel.py` | 潜在 None.append() 崩溃 |

另外统一了 43 处 FastAPI 权限依赖的写法（原先 `= None` 与无默认值两种写法混用，
违反「同一模块禁止混用两种风格」，且 `= None` 与 `SysUser` 标注自相矛盾）。
